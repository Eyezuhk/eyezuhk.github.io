Agentes de código com IA já são comuns em estações de trabalho de desenvolvedores. Codex, Cursor, Claude Code, Cline, Windsurf, JetBrains AI Assistant, GitHub Copilot e OpenCode conseguem ler código, alterar arquivos, chamar ferramentas externas, executar comandos e manter histórico de conversa.

Isso os torna uma fonte forense útil, e este guia é sobre onde encontrar essa evidência e como coletar com segurança.

## O que coletar primeiro

Para triagem rápida de uma estação de trabalho, comece por:

1. O diretório de dados de usuário do agente ou da IDE.
2. O projeto afetado, incluindo `.git/`, manifestos de pacote, lockfiles, scripts de build e qualquer instrução de agente em nível de projeto.
3. Bancos SQLite junto com seus arquivos `-wal`, `-shm` e de backup.
4. Logs da IDE, das extensões e do agente.
5. Histórico de shell, telemetria de execução de processos, telemetria de rede e timestamps do sistema de arquivos.

As perguntas que valem a pena responder são simples. O que o usuário pediu ao agente. Qual projeto e quais arquivos estavam envolvidos. Quais ferramentas e comandos o agente chamou. Qual saída esses comandos produziram. Quais arquivos mudaram. O agente instalou um pacote, baixou um binário, adicionou uma dependência, alterou um script de build ou se conectou a um serviço externo. Havia credenciais, chaves de API ou endpoints de LLM local configurados.

| Ferramenta                | Comece aqui                                                                                                                                                          | Evidência mais útil                                                                               |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |

## O padrão que se repete entre os agentes

O formato muda de ferramenta para ferramenta, mas a maioria dos agentes deixa as mesmas categorias de evidência.

O histórico de chat guarda os prompts do usuário, as respostas do modelo e, às vezes, arquivos anexados ou trechos de código selecionados. A atividade de ferramentas cobre leitura e edição de arquivos, buscas, ações no navegador, chamadas via MCP e outras invocações de ferramenta. A execução de comandos registra o que o agente propôs ou rodou, geralmente com saída padrão, saída de erro, código de saída e diretório de trabalho. O mapeamento de workspace conecta uma pasta de armazenamento com identificador opaco ao projeto que estava aberto. Alterações em arquivos aparecem como arquivos modificados, checkpoints, snapshots, histórico local, ou pelo próprio Git. A configuração cobre o provedor do modelo, a URL do endpoint, servidores MCP, regras customizadas, permissões, extensões e plugins em uso. Credenciais aparecem como chaves de API, tokens OAuth ou referências ao chaveiro do sistema operacional.

Uma transcrição não é prova de que um comando teve sucesso. Trate-a como evidência de intenção e de atividade do agente, e depois confirme com execução de processo, telemetria de endpoint, alterações em arquivo, histórico de shell, logs de gerenciador de pacotes e conexões de rede.

## Quando a preocupação é software ou dependência maliciosa

Um agente pode ser instruído a instalar uma biblioteca, corrigir um erro de dependência, baixar uma ferramenta ou configurar um ambiente. Isso pode ser totalmente legítimo, mas também é um caminho de ataque real que vale a pena checar.

Comece pela transcrição do agente e procure por comandos como:

```text
npm install
pnpm add
yarn add
pip install
uv add
poetry add
cargo add
go get
gem install
composer require
curl
wget
Invoke-WebRequest
irm
iex
chmod +x
powershell -enc
bash -c
```

Depois, inspecione o projeto em busca de mudanças em:

```text
package.json
package-lock.json
npm-shrinkwrap.json
pnpm-lock.yaml
yarn.lock
requirements.txt
pyproject.toml
poetry.lock
Pipfile.lock
Cargo.toml
Cargo.lock
go.mod
go.sum
Dockerfile
docker-compose.yml
Makefile
.github/workflows/
.git/hooks/
.vscode/tasks.json
```

Preste atenção especial a scripts de ciclo de vida de pacote, novos hooks do Git, mudanças em workflows de CI, binários novos, URLs remotas de download, scripts ofuscados e dependências vindas de registros pouco usuais.

Evidências que ajudam a confirmar o que aconteceu incluem timestamps de criação e modificação de arquivo, telemetria de processo do endpoint mostrando o gerenciador de pacotes e seus processos filhos, logs de navegador, proxy, DNS e firewall mostrando acesso a registros ou downloads, histórico de shell, caches e logs do gerenciador de pacotes, diffs e commits do Git, e novos autoruns, tarefas agendadas, serviços ou itens de inicialização.

A transcrição do agente pode explicar por que um pacote foi adicionado. O sistema operacional e os artefatos do projeto mostram o que de fato aconteceu.

## Cuidados na coleta

Não colete apenas o banco SQLite principal. Se a aplicação estava em execução, mudanças recentes ainda podem estar no write ahead log, e não no arquivo principal. Preserve estes juntos sempre que existirem:

```text
state.vscdb
state.vscdb-wal
state.vscdb-shm
state.vscdb.backup
```

Trabalhe sempre a partir de uma cópia forense. Abrir um banco SQLite ao vivo com um cliente normal pode alterar arquivos de journal, ou simplesmente falhar porque o banco está travado pela aplicação em execução.

Verifique também locais de armazenamento customizados. As variáveis de sobrescrita mais comuns são:

```text
CODEX_HOME
OLLAMA_MODELS
OPENCODE_DB
OPENCODE_CONFIG
OPENCODE_CONFIG_DIR
CLINE_DATA_DIR
```

O Cline também aceita o argumento explícito `--data-dir`. Instalações portáteis, perfis alternativos de IDE, desenvolvimento remoto, containers, WSL e pastas sincronizadas podem mover a evidência relevante para fora do caminho padrão.

Por fim, trate prompts, logs e configuração recuperados como sensíveis. Eles podem conter URLs de produção, código-fonte, credenciais, tokens, dados de cliente ou instruções internas.

## Evidência em nível de projeto

Não pare no diretório da aplicação. O próprio repositório pode conter instruções que moldaram o comportamento do agente. Arquivos e diretórios comuns para checar:

```text
AGENTS.md
CLAUDE.md
.cursorrules
.clinerules
.cline/
.opencode/
opencode.json
opencode.jsonc
mcp.json
.vscode/
.aiignore
```

Esses arquivos costumam ser mais importantes do que parecem à primeira vista. Um repositório malicioso pode usar instruções, configuração de MCP, hooks ou definições de tarefa para levar um agente a ler arquivos sensíveis, executar comandos, baixar conteúdo ou modificar o projeto por conta própria.

## Codex

O Codex guarda estado local sob `CODEX_HOME`. Quando essa variável não está configurada, o padrão é `.codex` dentro do home do usuário.

```text
C:\Users\<user>\.codex\
/home/<user>/.codex/
/Users/<user>/.codex/
```

Os principais artefatos de sessão são arquivos JSONL organizados por data:

```text
C:\Users\<user>\.codex\sessions\YYYY\MM\DD\
/home/<user>/.codex/sessions/YYYY/MM/DD/
/Users/<user>/.codex/sessions/YYYY/MM/DD/
```

Colete o diretório `CODEX_HOME` inteiro. Os arquivos de sessão podem conter metadados de diretório de trabalho, mensagens do usuário, mensagens do agente, chamadas de ferramenta, execução de comando, saída de ferramenta e operações em arquivo. Essa organização de sessão em JSONL por data está presente no código-fonte do Codex ([fonte](https://github.com/openai/codex/blob/main/codex-rs/app-server/tests/common/rollout.rs)).

Colete também a configuração e qualquer banco de estado local presente. O comportamento de autenticação depende da versão e da configuração. O `auth.json` pode existir sob `CODEX_HOME`, mas as credenciais também podem estar no chaveiro do sistema operacional, ou existir só durante a sessão ativa.

## Cursor

O Cursor usa um modelo de armazenamento derivado do VS Code. Colete tanto o armazenamento global quanto o de workspace.

```text
%APPDATA%\Cursor\User\globalStorage\
%APPDATA%\Cursor\User\workspaceStorage\

~/.config/Cursor/User/globalStorage/
~/.config/Cursor/User/workspaceStorage/

~/Library/Application Support/Cursor/User/globalStorage/
~/Library/Application Support/Cursor/User/workspaceStorage/
```

Os diretórios de workspace usam identificadores opacos. Preserve o `workspace.json`, que pode mapear a pasta de volta ao projeto, junto com o `state.vscdb` e seus arquivos auxiliares de SQLite. Material de suporte do Cursor identifica `workspaceStorage/<workspace-id>/state.vscdb` como fonte de estado de workspace e histórico de chat ([fonte](https://forum.cursor.com/t/agents-panel-right-sidebar-lost-session-list-no-way-to-restore/153481/4)).

As chaves e o esquema do banco mudam entre versões. Identifique as tabelas e chaves presentes na versão coletada em vez de assumir um esquema fixo, e correlacione o estado recuperado com o caminho do workspace, o histórico do Git e os arquivos modificados.

## Claude Code

O Claude Code guarda os dados da aplicação sob `.claude`.

```text
C:\Users\<user>\.claude\
/home/<user>/.claude/
/Users/<user>/.claude/
```

Os artefatos de sessão mais importantes ficam sob `projects/`:

```text
C:\Users\<user>\.claude\projects\
/home/<user>/.claude/projects/
/Users/<user>/.claude/projects/
```

Colete essas transcrições em JSONL junto com o histórico de prompts e os snapshots de arquivo:

```text
C:\Users\<user>\.claude\history.jsonl
C:\Users\<user>\.claude\file-history\

/home/<user>/.claude/history.jsonl
/home/<user>/.claude/file-history/

/Users/<user>/.claude/history.jsonl
/Users/<user>/.claude/file-history/
```

O Claude Code documenta `projects/` como dados de sessões passadas, `history.jsonl` como dados de recall de prompt, e `file-history/` como snapshots pré-edição usados para restauração de checkpoint ([fonte](https://code.claude.com/docs/en/claude-directory)). Diretórios adicionais como `plans/`, `tasks/`, `debug/`, `paste-cache/`, `shell-snapshots/`, `session-env/` e `backups/` podem ajudar na reconstrução da linha do tempo.

## Cline

O **Cline CLI** usa `.cline` por padrão:

```text
C:\Users\<user>\.cline\
/home/<user>/.cline/
/Users/<user>/.cline/
```

Colete o diretório inteiro. A documentação atual do Cline lista, sob esse local, configurações, configuração de provedor, regras e skills globais, estado de equipe, armazenamento de sessão, logs e plugins, e documenta o banco de sessão como SQLite ([fonte](https://docs.cline.bot/cli/cli-reference)).

Colete também a configuração do Cline em nível de projeto:

```text
.cline/
.cline/mcp.json
.cline/rules/
.cline/skills/
.cline/hooks/
.cline/plugins/
.cline/agents.yaml
```

Regras e hooks de ciclo de vida podem explicar como o Cline foi instruído a se comportar. A configuração de MCP pode identificar ferramentas locais, serviços remotos, credenciais ou fontes de dados às quais o agente tinha acesso.

Quando roda **como extensão de VS Code**, o Cline guarda seus dados nos diretórios padrão de dados de usuário do VS Code. Identifique o armazenamento de extensão relacionado ao Cline verificando as extensões instaladas e as pastas sob `globalStorage/`, em vez de depender de um nome de pasta interno fixo que valha para todas as versões.

## Windsurf

O Windsurf existe como editor independente e como plugins para várias IDEs. Trate cada um como uma fonte de evidência separada.

Para o **editor Windsurf**, comece pelo diretório de dados de usuário:

```text
%APPDATA%\Windsurf\User\
~/.config/Windsurf/User/
~/Library/Application Support/Windsurf/User/
```

Colete `globalStorage/`, `workspaceStorage/`, o `state.vscdb` e seus arquivos auxiliares de SQLite, o `workspace.json` e os logs do editor. Como em outros editores derivados do VS Code, o armazenamento de workspace conecta a atividade do agente a um projeto específico.

Para os **plugins do Windsurf**, colete os dados de aplicação e os logs da IDE hospedeira, em vez de assumir que todo plugin usa o mesmo layout do editor independente. O Windsurf documenta a coleta de log através do ambiente hospedeiro: os logs da extensão de VS Code ficam disponíveis via Developer: Show Logs e pelo canal de log do Windsurf, e os plugins de JetBrains podem gerar diagnósticos do Windsurf através do diretório de log da própria IDE ([fonte](https://docs.windsurf.com/de/troubleshooting/plugins-gathering-logs)). Em uma imagem forense, preserve os diagnósticos originais do plugin e os logs da IDE hospedeira antes de tentar reproduzir o problema.

## JetBrains AI Assistant

O JetBrains AI Assistant inclui recursos de chat e fluxos de trabalho com agente, capazes de fazer mudanças em várias etapas por todo o projeto, distribuídos pelas IDEs da JetBrains, em vez de um único produto independente. A JetBrains guarda o histórico de chat de IA separadamente por projeto ao longo das sessões da IDE ([fonte](https://www.jetbrains.com/help/ai-assistant/chat-mode.html)).

O principal ponto de coleta é a pasta `workspace/` dentro do diretório de configuração da IDE:

```text
%APPDATA%\JetBrains\<IDE><versão>\workspace\
~/.config/JetBrains/<IDE><versão>/workspace/
~/Library/Application Support/JetBrains/<IDE><versão>/workspace/
```

Esse diretório pode conter arquivos XML específicos de projeto com histórico de chat. A JetBrains documenta que esses arquivos podem incluir títulos de chat, identificadores de modelo ou agente, mensagens do usuário, mensagens do assistente e anexos de texto ([fonte](https://youtrack.jetbrains.com/articles/SUPPORT-A-4167/Export-AI-Assistant-chat-history-to-Markdown)).

Colete também os logs da IDE:

```text
%LOCALAPPDATA%\JetBrains\<IDE><versão>\log\
~/.cache/JetBrains/<IDE><versão>/log/
~/Library/Logs/JetBrains/<IDE><versão>/
```

O AI Assistant também pode manter um log de requisições `ai-assistant-requests.md` durante a sessão ativa. É um artefato útil de resposta ao vivo, mas não substitui os dados de workspace preservados, porque pode ser limpo ou desaparecer assim que a sessão termina ([fonte](https://www.jetbrains.com/help/ai-assistant/how-we-handle-your-code-and-data.html)).

## VS Code e extensões de IA

Para o VS Code em si, colete tanto o armazenamento global quanto o de workspace:

```text
%APPDATA%\Code\User\globalStorage\
%APPDATA%\Code\User\workspaceStorage\

~/.config/Code/User/globalStorage/
~/.config/Code/User/workspaceStorage/

~/Library/Application Support/Code/User/globalStorage/
~/Library/Application Support/Code/User/workspaceStorage/
```

A pasta de workspace costuma conter `workspace.json`, `state.vscdb`, dados específicos de cada extensão e, dependendo da versão instalada, arquivos de sessão de chat. Colete o diretório de workspace relevante por inteiro, junto com seus arquivos auxiliares de SQLite.

Para GitHub Copilot, Cline, Continue, Windsurf e outras extensões, colete também:

```text
User/settings.json
User/globalStorage/
extensions/
logs/
```

A configuração da extensão pode revelar qual provedor, servidor MCP, endpoint local ou modelo customizado estava em uso.

## OpenCode

O OpenCode documenta seu diretório local de dados de aplicação como:

```text
%USERPROFILE%\.local\share\opencode\
~/.local/share/opencode/
~/.local/share/opencode/
```

Colete o diretório inteiro. A documentação atual identifica `auth.json`, `log/` e `project/` dentro dele. O diretório `project/` guarda dados de sessão e mensagem específicos de cada projeto, o `auth.json` pode conter material de autenticação de provedor, e o `log/` ajuda na reconstrução de atividade ([fonte](https://opencode.ai/docs/troubleshooting/)).

Colete também a configuração global e de projeto. A configuração global normalmente fica sob `.config/opencode`, e os projetos podem conter `opencode.json`, `opencode.jsonc` ou uma pasta `.opencode/`. Verifique `OPENCODE_DB`, `OPENCODE_CONFIG` e `OPENCODE_CONFIG_DIR` antes de assumir os padrões ([fonte](https://opencode.ai/docs/config)).

## Plataformas de LLM local

Ollama e LM Studio não são agentes de código por si só. Eles importam porque agentes de código, extensões de IDE, scripts e aplicações locais podem usá-los como backend de modelo.

O diretório padrão de modelos do **Ollama** é:

```text
C:\Users\<user>\.ollama\models\
/usr/share/ollama/.ollama/models/
/Users/<user>/.ollama/models/
```

O caminho pode ser alterado pela variável `OLLAMA_MODELS`. No Windows, colete os logs de aplicação em `%LOCALAPPDATA%\Ollama\`. No Linux, revise a configuração do serviço systemd do Ollama e os logs do journal. No macOS, colete `~/.ollama/` e `~/.ollama/logs/`. O Ollama documenta seus locais padrão de modelo, a sobrescrita via `OLLAMA_MODELS`, e seu listener padrão de API em `127.0.0.1:11434` ([fonte](https://docs.ollama.com/faq)).

Um arquivo de modelo no disco prova que um modelo estava disponível localmente. Não prova um prompt, comando ou ação de agente específico. Isso deve ser recuperado a partir da aplicação cliente, da transcrição do agente, de logs de proxy, do histórico de shell ou da telemetria de endpoint.

O **LM Studio** guarda as conversas salvas como arquivos JSON:

```text
%USERPROFILE%\.lmstudio\conversations\
~/.lmstudio/conversations/
~/.lmstudio/conversations/
```

Esses arquivos são evidência de alto valor para atividade de chat local. O LM Studio documenta esse local e recomenda não depender de detalhes de esquema interno não documentados, então preserve o JSON original e faça o parsing a partir de uma cópia forense ([fonte](https://lmstudio.ai/docs/app/basics/chat)).

O diretório normal de modelos é:

```text
%USERPROFILE%\.lmstudio\models\
~/.lmstudio/models/
~/.lmstudio/models/
```

O usuário pode trocar o diretório de modelos pela própria aplicação, então confirme o local configurado em vez de assumir o padrão ([fonte](https://lmstudio.ai/docs/app/advanced/import-model)).

Se o servidor de API local do LM Studio estava habilitado, identifique o cliente local que o chamou. O listener padrão é `http://localhost:1234`. A autenticação ali é opcional, a menos que o usuário tenha configurado um token de API ([fonte](https://lmstudio.ai/docs/developer/rest/quickstart)).

## Fluxo prático de análise

1. Identifique a conta de usuário, o projeto relevante e a janela de tempo aproximada.
2. Preserve os diretórios completos de dados do agente, da IDE e do LLM local.
3. Colete os bancos SQLite junto com seus arquivos WAL, SHM e backup.
4. Mapeie os identificadores de workspace para caminhos de projeto usando `workspace.json`, timestamps, configuração e metadados do Git.
5. Extraia prompts, respostas, atividade de ferramentas, comandos, saídas, arquivos editados, configuração de MCP e configurações de provedor.
6. Revise mudanças em dependências, build, workflows, hooks e persistência, tanto no projeto quanto no sistema operacional.
7. Correlacione a linha do tempo reconstruída com evidência de endpoint, shell, rede e Git.
8. Revogue credenciais expostas junto ao provedor correspondente, e nunca teste chaves recuperadas contra sistemas de produção.

O objetivo não é recuperar o raciocínio interno de um modelo. É reconstruir a atividade observável: o que o usuário pediu, o que o agente tinha permissão para fazer, o que ele tentou, o que mudou, e o que de fato rodou na estação de trabalho.
