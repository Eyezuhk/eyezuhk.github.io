AI coding agents are now common on developer workstations. Codex, Cursor, Claude Code, Cline, Windsurf, JetBrains AI Assistant, GitHub Copilot and OpenCode can all read code, change files, call external tools, run commands and retain chat history.

That makes them a useful forensic source, and this guide is about where to find that evidence and how to collect it safely.

## What to collect first

If you need to triage a workstation quickly, start with:

1. The agent or IDE user data directory.
2. The affected project, including `.git/`, package manifests, lockfiles, build scripts and any project level agent instructions.
3. SQLite databases together with their `-wal`, `-shm` and backup files.
4. IDE, extension and agent logs.
5. Shell history, process execution telemetry, network telemetry and file system timestamps.

The questions worth answering are simple. What did the user ask the agent to do. Which project and files were involved. Which tools and commands did the agent invoke. What output did those commands produce. Which files changed. Did the agent install a package, download a binary, add a dependency, alter a build script or connect to an external service. Were credentials, API keys or local LLM endpoints configured.

| Tool                      | Start here                                                                                                                                                              | Most useful evidence                                                      |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Codex                     | `%USERPROFILE%\.codex\` → `~/.codex/` → `~/.codex/`                                                                                                                     | JSONL session transcripts, working directories, tool calls, configuration |
| Cursor                    | `%APPDATA%\Cursor\User\` → `~/.config/Cursor/User/` → `~/Library/Application Support/Cursor/User/`                                                                      | Workspace mapping, SQLite state, chats, agent activity                    |
| Claude Code               | `%USERPROFILE%\.claude\` → `~/.claude/` → `~/.claude/`                                                                                                                  | Full JSONL sessions, prompt history, tool results, file snapshots         |
| Cline CLI                 | `%USERPROFILE%\.cline\` → `~/.cline/` → `~/.cline/`                                                                                                                     | Session database, provider settings, logs, rules, hooks                   |

## The pattern that repeats across agents

The formats differ from tool to tool, but most agents leave the same categories of evidence.

Chat history holds user prompts, model responses and sometimes attached files or selected code. Tool activity covers file reads, edits, searches, browser actions, MCP calls and other tool invocations. Command execution records what the agent proposed or ran, often with standard output, standard error, exit status and working directory. Workspace mapping links an opaque storage folder back to the project that was open. File changes show up as modified files, checkpoints, snapshots, local history or through Git itself. Configuration covers the model provider, endpoint URL, MCP servers, custom rules, permissions, extensions and plugins in use. Credentials show up as API keys, OAuth tokens or references to an operating system keyring.

A transcript is not proof that a command succeeded. Treat it as evidence of intent and agent activity, then corroborate it with process execution, endpoint telemetry, file changes, shell history, package manager logs and network connections.

## When the concern is malicious software or dependencies

An agent can be asked to install a library, fix a dependency error, download a tool or set up an environment. That can be entirely legitimate, but it is also a real attack path worth checking.

Start with the agent transcript and look for commands like:

```text
npm install
pnpm add
yarn add
pip install
uv add
poetry add
cargo add
go get
gem install
composer require
curl
wget
Invoke-WebRequest
irm
iex
chmod +x
powershell -enc
bash -c
```

Then inspect the project for changes to:

```text
package.json
package-lock.json
npm-shrinkwrap.json
pnpm-lock.yaml
yarn.lock
requirements.txt
pyproject.toml
poetry.lock
Pipfile.lock
Cargo.toml
Cargo.lock
go.mod
go.sum
Dockerfile
docker-compose.yml
Makefile
.github/workflows/
.git/hooks/
.vscode/tasks.json
```

Pay close attention to package lifecycle scripts, new Git hooks, CI workflow changes, newly added binaries, remote download URLs, obfuscated scripts and dependencies pulled from unfamiliar registries.

Corroborating evidence worth checking includes file creation and modification timestamps, endpoint process telemetry showing the package manager and its child processes, browser, proxy, DNS and firewall logs showing registry or download access, shell history, package manager caches and logs, Git diffs and commits, and any new autoruns, scheduled tasks, services or startup items.

The agent transcript can explain why a package was added. The operating system and project artifacts show what actually happened.

## Collection cautions

Do not collect only the main SQLite database. If the application was running, recent changes may still sit in the write ahead log rather than the main file. Preserve these together whenever they exist:

```text
state.vscdb
state.vscdb-wal
state.vscdb-shm
state.vscdb.backup
```

Work from a forensic copy. Opening a live SQLite database with a normal client can alter journal files, or simply fail because the database is locked by the running application.

Also check for custom storage locations. Common overrides include:

```text
CODEX_HOME
OLLAMA_MODELS
OPENCODE_DB
OPENCODE_CONFIG
OPENCODE_CONFIG_DIR
CLINE_DATA_DIR
```

Cline also accepts an explicit `--data-dir` argument. Portable installations, alternate IDE profiles, remote development, containers, WSL and synced folders can all move relevant evidence away from the default path.

Finally, treat recovered prompts, logs and configuration as sensitive. They can contain production URLs, source code, credentials, tokens, customer data or internal instructions.

## Project level evidence

Do not stop at the application directory. The repository itself can contain instructions that shaped the agent's behavior. Common files and directories to check:

```text
AGENTS.md
CLAUDE.md
.cursorrules
.clinerules
.cline/
.opencode/
opencode.json
opencode.jsonc
mcp.json
.vscode/
.aiignore
```

These are often more important than they first look. A malicious repository can use instructions, MCP configuration, hooks or task definitions to steer an agent into reading sensitive files, running commands, downloading content or modifying the project on its own.

## Codex

Codex stores local state under `CODEX_HOME`. When that variable is not set, the default is `.codex` inside the user's home directory.

```text
C:\Users\<user>\.codex\
/home/<user>/.codex/
/Users/<user>/.codex/
```

The primary session artifacts are date partitioned JSONL rollout files:

```text
C:\Users\<user>\.codex\sessions\YYYY\MM\DD\
/home/<user>/.codex/sessions/YYYY/MM/DD/
/Users/<user>/.codex/sessions/YYYY/MM/DD/
```

Collect the full `CODEX_HOME` directory. Session files can contain working directory metadata, user messages, agent messages, tool calls, command execution, tool output and file operations. The date based JSONL session layout is present in the Codex source ([source](https://github.com/openai/codex/blob/main/codex-rs/app-server/tests/common/rollout.rs)).

Also collect configuration and any local state databases present. Authentication behavior depends on version and configuration. `auth.json` may exist under `CODEX_HOME`, but credentials can also live in the operating system keyring or only for the active session.

## Cursor

Cursor uses a VS Code derived storage model. Collect both global and workspace storage.

```text
%APPDATA%\Cursor\User\globalStorage\
%APPDATA%\Cursor\User\workspaceStorage\

~/.config/Cursor/User/globalStorage/
~/.config/Cursor/User/workspaceStorage/

~/Library/Application Support/Cursor/User/globalStorage/
~/Library/Application Support/Cursor/User/workspaceStorage/
```

Workspace directories use opaque identifiers. Preserve `workspace.json`, which can map the folder back to a project, together with `state.vscdb` and its SQLite sidecars. Cursor support material identifies `workspaceStorage/<workspace-id>/state.vscdb` as a source of workspace state and chat history ([source](https://forum.cursor.com/t/agents-panel-right-sidebar-lost-session-list-no-way-to-restore/153481/4)).

Database keys and schemas change between releases. Identify the tables and keys present in the collected version rather than assuming a fixed schema, and correlate the recovered state with the workspace path, Git history and modified files.

## Claude Code

Claude Code stores its application data under `.claude`.

```text
C:\Users\<user>\.claude\
/home/<user>/.claude/
/Users/<user>/.claude/
```

The most important session artifacts sit under `projects/`:

```text
C:\Users\<user>\.claude\projects\
/home/<user>/.claude/projects/
/Users/<user>/.claude/projects/
```

Collect those JSONL transcripts together with prompt history and file snapshots:

```text
C:\Users\<user>\.claude\history.jsonl
C:\Users\<user>\.claude\file-history\

/home/<user>/.claude/history.jsonl
/home/<user>/.claude/file-history/

/Users/<user>/.claude/history.jsonl
/Users/<user>/.claude/file-history/
```

Claude Code documents `projects/` as past session data, `history.jsonl` as prompt recall data and `file-history/` as pre edit snapshots used for checkpoint restoration ([source](https://code.claude.com/docs/en/claude-directory)). Additional directories such as `plans/`, `tasks/`, `debug/`, `paste-cache/`, `shell-snapshots/`, `session-env/` and `backups/` can help with timeline reconstruction.

## Cline

**Cline CLI** uses `.cline` by default:

```text
C:\Users\<user>\.cline\
/home/<user>/.cline/
/Users/<user>/.cline/
```

Collect the entire directory. Current Cline documentation lists settings, provider configuration, global rules and skills, team state, session storage, logs and plugins under this location, and documents the session database as SQLite ([source](https://docs.cline.bot/cli/cli-reference)).

Also collect the project level Cline configuration:

```text
.cline/
.cline/mcp.json
.cline/rules/
.cline/skills/
.cline/hooks/
.cline/plugins/
.cline/agents.yaml
```

Rules and lifecycle hooks can explain how Cline was instructed to behave. MCP configuration may identify local tools, remote services, credentials or data sources the agent had access to.

**As a VS Code extension**, Cline stores its data under the standard VS Code user data directories instead. Identify Cline related extension storage by checking installed extensions and the folders under `globalStorage/`, rather than relying on one fixed internal folder name across every version.

## Windsurf

Windsurf ships as a standalone editor and as plugins for several IDEs. Treat those as separate evidence sources.

For the **Windsurf Editor**, start with its user data directory:

```text
%APPDATA%\Windsurf\User\
~/.config/Windsurf/User/
~/Library/Application Support/Windsurf/User/
```

Collect `globalStorage/`, `workspaceStorage/`, `state.vscdb` and its SQLite sidecars, `workspace.json`, and editor logs. As with other VS Code derived editors, workspace storage links agent activity to a specific project.

For **Windsurf plugins**, collect the host IDE's application data and logs rather than assuming every plugin uses the standalone editor layout. Windsurf documents log collection through the host environment. VS Code extension logs are available through Developer: Show Logs and the Windsurf log channel, and JetBrains plugins can generate Windsurf diagnostics through the IDE log directory ([source](https://docs.windsurf.com/de/troubleshooting/plugins-gathering-logs)). For a forensic image, preserve the original plugin diagnostics and host logs before attempting to reproduce the issue.

## JetBrains AI Assistant

JetBrains AI Assistant includes chat features and agent capable coding workflows across JetBrains IDEs, rather than a single standalone product. JetBrains stores AI chat history separately for each project across IDE sessions ([source](https://www.jetbrains.com/help/ai-assistant/chat-mode.html)).

The main collection point is the `workspace/` folder inside the IDE configuration directory:

```text
%APPDATA%\JetBrains\<IDE><version>\workspace\
~/.config/JetBrains/<IDE><version>/workspace/
~/Library/Application Support/JetBrains/<IDE><version>/workspace/
```

This directory can contain project specific XML files with chat history. JetBrains documents that these files may include chat titles, model or agent identifiers, user messages, assistant messages and text attachments ([source](https://youtrack.jetbrains.com/articles/SUPPORT-A-4167/Export-AI-Assistant-chat-history-to-Markdown)).

Collect IDE logs as well:

```text
%LOCALAPPDATA%\JetBrains\<IDE><version>\log\
~/.cache/JetBrains/<IDE><version>/log/
~/Library/Logs/JetBrains/<IDE><version>/
```

AI Assistant can also maintain an `ai-assistant-requests.md` request log during the active session. This is a useful live response artifact, but it is not a substitute for preserved workspace data, since it can be cleaned up or disappear once the session ends ([source](https://www.jetbrains.com/help/ai-assistant/how-we-handle-your-code-and-data.html)).

## VS Code and AI extensions

For VS Code itself, collect both global and workspace storage:

```text
%APPDATA%\Code\User\globalStorage\
%APPDATA%\Code\User\workspaceStorage\

~/.config/Code/User/globalStorage/
~/.config/Code/User/workspaceStorage/

~/Library/Application Support/Code/User/globalStorage/
~/Library/Application Support/Code/User/workspaceStorage/
```

The workspace folder often contains `workspace.json`, `state.vscdb`, extension specific data and, depending on the installed version, chat session files. Collect the entire relevant workspace directory together with its SQLite sidecars.

For GitHub Copilot, Cline, Continue, Windsurf and other extensions, also collect:

```text
User/settings.json
User/globalStorage/
extensions/
logs/
```

The extension configuration can reveal which provider, MCP server, local endpoint or custom model was in use.

## OpenCode

OpenCode documents its local application data directory as:

```text
%USERPROFILE%\.local\share\opencode\
~/.local/share/opencode/
~/.local/share/opencode/
```

Collect the entire directory. Current documentation identifies `auth.json`, `log/` and `project/` inside it. The `project/` directory holds project specific session and message data, `auth.json` can contain provider authentication material, and `log/` helps with reconstructing activity ([source](https://opencode.ai/docs/troubleshooting/)).

Also collect global and project configuration. Global configuration normally sits under `.config/opencode`, and projects may contain `opencode.json`, `opencode.jsonc` or a `.opencode/` folder. Check `OPENCODE_DB`, `OPENCODE_CONFIG` and `OPENCODE_CONFIG_DIR` before assuming the defaults ([source](https://opencode.ai/docs/config)).

## Local LLM platforms

Ollama and LM Studio are not coding agents by themselves. They matter because coding agents, IDE extensions, scripts and local applications can use them as a model backend.

**Ollama's** default model directory is:

```text
C:\Users\<user>\.ollama\models\
/usr/share/ollama/.ollama/models/
/Users/<user>/.ollama/models/
```

The path can be changed through `OLLAMA_MODELS`. On Windows, collect application logs from `%LOCALAPPDATA%\Ollama\`. On Linux, review the Ollama systemd service configuration and journal logs. On macOS, collect `~/.ollama/` and `~/.ollama/logs/`. Ollama documents its default model locations, the `OLLAMA_MODELS` override, and its default API listener at `127.0.0.1:11434` ([source](https://docs.ollama.com/faq)).

A model file on disk proves that a model was available locally. It does not prove a specific prompt, command or agent action. Recover those from the client application, the agent transcript, proxy logs, shell history or endpoint telemetry.

**LM Studio** stores saved conversations as JSON files:

```text
%USERPROFILE%\.lmstudio\conversations\
~/.lmstudio/conversations/
~/.lmstudio/conversations/
```

These files are high value evidence for local chat activity. LM Studio documents the location and advises against relying on undocumented internal schema details, so preserve the original JSON and parse it from a forensic copy ([source](https://lmstudio.ai/docs/app/basics/chat)).

The normal model directory is:

```text
%USERPROFILE%\.lmstudio\models\
~/.lmstudio/models/
~/.lmstudio/models/
```

Users can change the model directory inside the application, so verify the configured location rather than assuming the default ([source](https://lmstudio.ai/docs/app/advanced/import-model)).

If LM Studio's local API server was enabled, identify the local client that called it. The default listener is `http://localhost:1234`. Authentication is optional there unless the user configured an API token ([source](https://lmstudio.ai/docs/developer/rest/quickstart)).

## Practical analysis workflow

1. Identify the user account, the relevant project and the approximate time window.
2. Preserve the full agent, IDE and local LLM data directories.
3. Collect SQLite databases together with their WAL, SHM and backup files.
4. Map workspace identifiers to project paths using `workspace.json`, timestamps, configuration and Git metadata.
5. Extract prompts, responses, tool activity, commands, output, edited files, MCP configuration and provider settings.
6. Review dependency, build, workflow, hook and persistence changes in the project and the operating system.
7. Correlate the reconstructed timeline with endpoint, shell, network and Git evidence.
8. Revoke exposed credentials through the relevant provider, and never test recovered keys against production systems.

The goal is not to recover a model's internal reasoning. It is to reconstruct observable activity: what the user requested, what the agent was allowed to do, what it attempted, what it changed, and what actually ran on the workstation.
